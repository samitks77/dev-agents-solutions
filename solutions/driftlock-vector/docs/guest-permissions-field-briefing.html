Problem statement and outcomes

This section translates architecture into business impact.

What is hard today

  • Guest inventory lives in one place, but effective cloud access is spread across many control planes.
  • RBAC-only views are incomplete when PIM, deny assignments, and group transitivity are not included.
  • Service-native ACLs create blind spots if only management-plane permissions are analyzed.
  • Manual evidence gathering is slow and not repeatable enough for governance reviews.

What this solution changes

  • One repeatable collection workflow across Entra, Azure RBAC, and data-plane modules.
  • One effective-permissions output model with direct, inherited, group, deny, and PIM state.
  • One telemetry plane for run quality, failures, coverage, and trending.
  • One dashboard and briefing motion for internal and customer governance discussions.

Architecture blueprint

Designed to separate infrastructure, identity governance, runtime execution, and presentation.

End-to-end flow

LAYER 1
Operator and agent control plane
Human operators or M365 agent initiate and monitor runs.
LAYER 2
Runtime execution host
Container Apps Job executes collection and resolution stages.
LAYER 3
Permission source systems
Graph, ARM, and service APIs provide identity and access evidence.
LAYER 4
Evidence and observability
Snapshots in storage, telemetry in Log Analytics, dashboards in Grafana.
Architectural principle Infrastructure deployment and privileged identity grants are separated on purpose. This enables safer approvals, cleaner audits, and controlled change management.

Effective permission resolver logic

This is the core algorithmic value of the solution.

Resolution sequence

STEP 1
Normalize principals
Map guest principal IDs and transitive group IDs into a single subject set.
STEP 2
Expand scope inheritance
Apply assignment inheritance from management group to resource scope.
STEP 3
Merge role semantics
Join role assignments to role definitions and extract control/data actions.
STEP 4
Apply deny and PIM state
Constrain effective grants by deny assignments and eligible/active timing.
STEP 5
Emit final evidence
Write effective rows and telemetry for dashboards and audits.
Critical design decision The resolver is deterministic and evidence-backed. Every effective row should be traceable to source artifacts for auditability and remediation confidence.

Security and governance model

Designed for least privilege, auditability, and controlled autonomy.

Identity separation

  • Runtime uses managed identity.
  • Operators use human RBAC identities.
  • Optional agent uses control-plane boundaries.

Change-control separation

  • Infrastructure deployment is one gate.
  • Privileged identity grants are separate gate.
  • Runtime changes are versioned and testable.

Audit and evidence

  • Deployment history in Azure deployment records.
  • Execution traces in Log Analytics.
  • Snapshot artifacts in storage for verification.
Non-negotiable production rule Do not blend infrastructure deployment with privileged identity grants in one opaque step. Keep approvals and logs separate.

Objection handling — plain English answers

Use these answers directly in live conversations.

Is RBAC enough to know guest access?
RBAC is foundational and authoritative for Azure management-plane access. We add directory transitivity, deny assignments, PIM state, and optional service data-plane signals so the final view reflects real effective access, not partial access.
Do we need the runtime container if we have an agent?
Yes. The agent is the control plane (trigger and status). The runtime container/job is the data engine that performs heavy collection and resolution at enterprise scale.
Can this run in production safely?
Yes, with least-privilege identity grants and change-control gates. We included validation, smoke tests, and operations runbooks specifically to support safe production operation.
How quickly can we pilot this with a customer?
Typically one to two weeks for bootstrap, identity approvals, runtime onboarding, and first dashboard cycle, depending on approval lead times.
What is the biggest implementation risk?
Under-scoped permissions or skipped governance gates. Both lead to partial visibility or failed runs. This package addresses that risk with explicit staged deployment and validation scripts.
