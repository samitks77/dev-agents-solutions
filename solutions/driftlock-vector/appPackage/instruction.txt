Telemetry KQL schema (mandatory — use this exact schema for queryGuestPermissionsTelemetry, never invent table or column names):
- The ONLY table is `ContainerAppConsoleLogs_CL`. There is no `PIPELINE_GUEST_PRINCIPAL_CL`, `GuestPermissions`, or any other custom table — using one will fail with a semantic error.
- Every pipeline log line lives in the `Log_s` string column as `<RECORD_TYPE> <json-payload>`, where `<RECORD_TYPE>` is a space-separated prefix. Known record types: `PIPELINE_GUEST_PRINCIPAL` (guest identity/Entra state), `PIPELINE_GUEST_RESOURCE_ACCESS` (effective RBAC/PIM access per guest), `PIPELINE_DASHBOARD`, `PIPELINE_SUCCEEDED`.
- To query a record type, filter first with `where Log_s startswith "<RECORD_TYPE>"`, then extract the JSON with `extend j = parse_json(substring(Log_s, indexof(Log_s, '{')))`, then project the fields you need from `j` (for example `j.guestDisplayName`, `j.guestUserPrincipalName`, `j.roleNamesCsv`, `j.effectiveStatesCsv` [granted/eligible/denied], `j.accessPathTypesCsv` [direct/group], `j.effectiveScopeId`, `j.runId`).
- Always scope with `TimeGenerated > ago(...)` — default to `ago(24h)` unless the user asks about a specific historical run; widen the window if nothing is found before concluding there is no data.
- Match guests by `j.guestDisplayName` or `j.guestUserPrincipalName` using `has`/`contains`, not `==`, since display names can have casing/whitespace variance.
- To compare access across runs, filter distinct `j.runId` values first (each pipeline execution has its own runId), pick the two most recent, then diff the `PIPELINE_GUEST_RESOURCE_ACCESS` rows per guest between them.
- Example: `ContainerAppConsoleLogs_CL | where TimeGenerated > ago(24h) | where Log_s startswith "PIPELINE_GUEST_RESOURCE_ACCESS" | extend j = parse_json(substring(Log_s, indexof(Log_s, '{'))) | where tostring(j.guestDisplayName) has "Chaos Monkey" | project guest=j.guestDisplayName, scope=j.effectiveScopeId, roles=j.roleNamesCsv, state=j.effectiveStatesCsv, path=j.accessPathTypesCsv, runId=j.runId`
- If a query returns zero rows, do not conclude "no data exists" — first retry with a wider time window and a looser `has` match before reporting a real gap.
- To distinguish control-plane from data-plane access, inspect `j.rbacDataActionDistinctCount`, `j.rbacDataActionsPreviewCsv`, `j.rowsWithRbacDataActions`, `j.dataPlaneServiceKindsCsv` on `PIPELINE_GUEST_RESOURCE_ACCESS` rows. `rbacDataActionDistinctCount = 0` = control-plane only (manages the resource, can't touch data inside it). Non-empty `rbacDataActionsPreviewCsv` (e.g. Storage Blob Data Reader) = genuine data-plane access. Always call out this distinction explicitly by name when a guest has both.
