🏗️ Steps 1–4 — Build the test service principal

Create an isolated app registration, give it a short-lived secret, and confirm it can authenticate. Nothing here touches an existing workload.

Step 1 Create a test app registration

  1. Go to the Microsoft Entra admin center
  2. Navigate to Identity → Applications → App registrations
  3. Click + New registration
  4. Enter:
    • Name: POC-RiskyWorkloadIdentity
    • Supported account types: Accounts in this organizational directory only
  5. Click Register
  6. On the Overview page, copy the Application (client) ID — you'll need it later

Step 2 Create a client secret

  1. In the app registration you just created, go to Certificates & secrets
  2. Click + New client secret
  3. Enter:
    • Description: POC-Secret
    • Expires: 7 days (or a custom short duration for safety)
  4. Click Add
  5. Immediately copy the secret Value — it won't be shown again

Step 3 Note the service principal object ID

  1. Go to Identity → Applications → Enterprise applications
  2. Search for POC-RiskyWorkloadIdentity
  3. Click it and copy the Object ID from the Overview page
⚠️ Don't confuse the two object IDs This is the Service Principal ID — it is different from the App Registration Object ID. Identity Protection APIs expect the service principal object ID; using the wrong one silently fails to flag anything.

Step 4 Test that the service principal can authenticate

  1. Open PowerShell (or any REST client like Postman)
  2. Run:
PowerShell 
$body = @{
    grant_type    = "client_credentials"
    client_id     = "<Application (client) ID from Step 1>"
    client_secret = "<Secret Value from Step 2>"
    scope         = "https://graph.microsoft.com/.default"
}
Invoke-RestMethod -Uri "https://login.microsoftonline.com/<Your Tenant ID>/oauth2/v2.0/token" `
    -Method POST -Body $body -ContentType "application/x-www-form-urlencoded"
✅ Expected result A response containing token_type: Bearer and expires_in: 3599.

🛡️ Steps 5–9 — Protect, simulate, and prove

Create the Conditional Access policy in report-only mode, generate a risk signal, then verify both the detection and the CA decision.

Step 5 Create a Conditional Access policy for risky workload identities

  1. Go to Entra admin center → Protection → Conditional Access → Policies
  2. Click + New policy
  3. Configure:
    • Name: POC - Block Risky Workload Identities
    • What does this policy apply to?: select Workload identities
    • Include: Select service principals → search for and select all POC SPs (POC-RiskyWorkloadIdentity, POC-Test-A-AdminConfirm, POC-Test-B-BackdoorCred, POC-Test-C-FabricAccess, POC-Test-D-BurstSignIn)
    • Target resources → Cloud apps: All cloud apps
    • Conditions → Service principal risk: set to Yes (Configure) → check High and Medium
    • Grant: select Block access
    • Enable policy: set to Report-only
  4. Click Create
🧪 Why report-only first Report-only mode logs the Conditional Access decision without actually blocking the sign-in. This is safe for initial testing — you get the full evaluation trail with none of the risk.

📊 Understanding risk levels

What actually drives High, Medium, and Low — and which of those you can realistically produce in a lab.

What drives each risk level?

Risk levelTriggerDetection typeHow it's generated
High Admin manually confirms compromise via the confirmCompromised API adminConfirmedServicePrincipalCompromised Manual — admin action via Graph API or portal
High Credentials found leaked (public GitHub repo, paste site, dark web) leakedCredentials Automatic — Microsoft Threat Intelligence
Medium Anomalous sign-in pattern — unusual IP, geography, or token properties suspiciousSignIns Automatic — Entra ML-based detection
Medium Service principal activity deviates significantly from its baseline anomalousServicePrincipalActivity Automatic — Entra behavioral analytics
Medium Sign-in from an IP associated with known malicious activity maliciousApplication Automatic — Microsoft Threat Intelligence
Low Minor behavioral anomalies not yet meeting the medium confidence threshold anomalousServicePrincipalActivity (low confidence) Automatic — Entra ML-based detection

🧭 What this means for the POC

  • Step 6 uses confirmCompromised, which always produces High risk — it is an explicit admin assertion and Entra treats it as the highest-confidence signal.
  • Medium and Low risk levels are generated automatically by Entra's ML-based detections when real anomalous behavior is observed in production (sign-in from a TOR exit node, unusual geography, rapid multi-resource access).
  • These cannot be easily simulated in a lab without generating genuinely anomalous traffic patterns.

🎯 Why the CA policy targets Medium and High

In Step 5 the policy triggers on both Medium and High risk. That ensures, in production:

  • Admin-confirmed compromises (High) → blocked immediately
  • ML-detected anomalies (Medium) → also caught and blocked before escalation
  • Low risk is excluded to avoid false positives on minor behavioral noise

🤔 Why we use confirmCompromised in the POC

The single most common customer question — and the answer that keeps the demo credible.

Why don't these activities automatically surface the SP in the Risky workload identities blade?
The blade only shows service principals that have a risk detection attached. Risk detections are created in exactly two ways: automatically by Entra's ML engine and Microsoft Threat Intelligence, or manually by an admin confirming compromise.

1️⃣ Automatic detections (production)

In a production tenant, Entra's ML engine and Microsoft Threat Intelligence automatically create risk detections. In a fresh POC tenant, none of them can fire — and here's precisely why:

DetectionHow it worksWhy it won't fire in a POC
anomalousServicePrincipalActivity ML compares current sign-in behavior against the SP's historical baseline (IP ranges, resources accessed, timing patterns) No baseline exists. These SPs were created minutes ago. Entra needs weeks of sign-in history to establish what's "normal" before it can detect what's "anomalous."
suspiciousSignIns ML detects unusual IP, impossible travel, or known malicious infrastructure New SPs have no "usual" IP. Every IP is equally new — there's nothing to flag as unusual.
leakedCredentials Microsoft scans GitHub, paste sites, and the dark web for exposed Azure credentials Only fires if credentials are actually published to a source Microsoft monitors. This takes ~8 hours even when deliberately triggered.
maliciousApplication Microsoft Threat Intelligence flags apps associated with known attack campaigns Only applies to apps in Microsoft's threat database — test apps won't match.

2️⃣ Manual confirmation (POC and production)

The confirmCompromised API creates an adminConfirmedServicePrincipalCompromised risk detection. This is not a POC-only workaround — it is a production feature used by SOC teams as their response action when they discover a compromised SP through:

🛰️ SIEM alerts (Sentinel, Splunk)
📜 Audit log monitoring rules
🎯 Threat intelligence feeds
🚑 Incident response investigations

🎤 How to explain this to your customer

"In production, Entra's ML builds a behavioral baseline for each service principal over weeks of sign-in data. When behavior deviates — a new resource, a new IP, a burst pattern — the SP automatically appears in the Risky workload identities blade without admin action.

In this POC, these SPs are brand new with no history, so the ML has no baseline to compare against. We use confirmCompromised to simulate the end-state — this is the same API your SOC would call after investigating a real alert.

The Conditional Access enforcement is identical regardless of the source. Whether the risk came from ML detection or admin confirmation, the block is the same AADSTS53003." Use verbatim — it pre-empts the "so this is fake" objection.

🔑 Test B — Suspicious credential addition (backdoor persistence)

What it proves: an attacker who gains access to an app registration can add a second client secret as a persistence mechanism. This is detectable via audit logs and warrants confirming the SP as compromised.

Service principal: POC-Test-B-BackdoorCred

🎬 Why this SP is confirmed compromised The SOC's audit log monitoring rule fires on Update application – Certificates and secrets management. Investigation reveals that an unknown actor added a second credential named backdoor-secret to an existing application. This is a classic persistence attack — MITRE ATT&CK T1098.001 (Account Manipulation: Additional Cloud Credentials). The attacker now has their own key to the application, independent of the original secret. The SOC confirms the SP as compromised to trigger Conditional Access protection while the incident is investigated.

Steps

  1. Generate a baseline sign-in for the SP:
PowerShell 
$body = @{
    grant_type    = "client_credentials"
    client_id     = "<POC-Test-B Application (client) ID>"
    client_secret = "<POC-Test-B Secret Value>"
    scope         = "https://graph.microsoft.com/.default"
}
Invoke-RestMethod -Uri "https://login.microsoftonline.com/<Your Tenant ID>/oauth2/v2.0/token" `
    -Method POST -Body $body -ContentType "application/x-www-form-urlencoded"
  1. Simulate the attacker adding a backdoor credential:
    • Go to Entra admin center → Identity → Applications → App registrations
    • Find POC-Test-B-BackdoorCred → Certificates & secrets
    • Click + New client secret
    • Enter description: backdoor-secret → click Add
    • The app now has 2 credentials — the original POC-Secret and the attacker's backdoor-secret
  2. Verify the audit trail (wait 15–20 minutes for audit log propagation):
    • Go to Entra admin center → Identity → Monitoring → Audit logs
    • Filter by Service: Core Directory, Activity: Update application – Certificates and secrets management
    • Find the entry for POC-Test-B-BackdoorCred
    • The Modified Properties section shows the KeyDescription field now containing both credentials

What to show the customer

  • Adding a credential to an app registration is a silent persistence technique — no alert by default.

📊 Test C — Anomalous Fabric access by a workload identity

What it proves: a service principal that has never accessed Fabric suddenly requests a Fabric token — this anomalous resource-access pattern is a risk indicator, and CA can block it.

Service principal: POC-Test-C-FabricAccess

🎬 Why this SP is confirmed compromised Sign-in logs show that POC-Test-C-FabricAccess requested a token for Power BI / Fabric for the first time ever. This SP was originally provisioned to access only Azure SQL. A sudden pivot to Fabric suggests an attacker is using compromised credentials to explore what data they can reach. The SOC investigates the anomalous resource access and confirms the SP as compromised.

Prerequisites

  • A Microsoft Fabric capacity provisioned in your tenant (even a trial capacity works)
  • Fabric API permissions granted to the service principal

Step C.1 Grant Fabric API permissions to the SP

  1. Go to Entra admin center → Identity → Applications → App registrations
  2. Select POC-Test-C-FabricAccess
  3. Go to API permissions → + Add a permission
  4. Select APIs my organization uses → search for Power BI Service (Fabric uses the Power BI API surface)
  5. Select Application permissions → check Tenant.Read.All (or Workspace.Read.All for more limited scope)
  6. Click Add permissions
  7. Click Grant admin consent for <Your Tenant> → Yes

Step C.2 Access Fabric (anomalous first-time access)

PowerShell 
$body = @{
    grant_type    = "client_credentials"
    client_id     = "<POC-Test-C Application (client) ID>"
    client_secret = "<POC-Test-C Secret Value>"
    scope         = "https://analysis.windows.net/powerbi/api/.default"
}
$token = (Invoke-RestMethod -Uri "https://login.microsoftonline.com/<Your Tenant ID>/oauth2/v2.0/token" `
    -Method POST -Body $body -ContentType "application/x-www-form-urlencoded").access_token

# Call Fabric/Power BI API to list workspaces
$headers = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Uri "https://api.fabric.microsoft.com/v1/workspaces" `
    -Headers $headers -Method GET

Confirm you get a response listing Fabric workspaces — it may be empty, and that's fine. The point is that the SP now has Fabric activity in sign-in logs.

🎤 Key point for the customer In production, Entra's ML engine would detect this as anomalousServicePrincipalActivity — an SP that historically only accesses SQL suddenly pivoting to Fabric. In the POC, we simulate the SOC's response to that detection.

Step C.3 SOC responds: confirm compromised

Graph 
POST https://graph.microsoft.com/v1.0/identityProtection/riskyServicePrincipals/confirmCompromised

{
  "servicePrincipalIds": ["<POC-Test-C Service Principal Object ID>"]
}

Click Run query — expect 204 No Content.

Step C.4 Report-only

  1. Re-run the exact same PowerShell from Step C.2
  2. With the CA policy in report-only mode:
    • The Fabric API call will succeed
    • But the CA decision is logged in sign-in logs

Step C.5 Block mode

  1. Go to Conditional Access → Policies → open POC - Block Risky Workload Identities
  2. Change Enable policy to On → Save
  3. Re-run the PowerShell from Step C.2
  4. The token request will fail: AADSTS53003 — Access has been blocked by Conditional Access policies. The SP cannot obtain a token for Fabric at all.

Step C.6 Verify in sign-in logs

  1. Go to Entra admin center → Identity → Monitoring → Sign-in logs
  2. Switch to Service principal sign-ins
  3. Filter by Application: POC-Test-C-FabricAccess
  4. Click into the sign-in entries:
    • Resource: Power BI Service (Fabric)
    • Conditional Access tab shows the policy and result (reportOnlyFailure or failure)

What to show the customer

  • An SP that suddenly accesses a new resource it never used before is a red flag — this is the kind of behavioral anomaly Entra's ML detects in production.
  • Workload Identity Protection works across all Entra-integrated resources, including Fabric.
  • A compromised SP is blocked from accessing Fabric even though it has valid API permissions.
  • The CA policy applies at the token issuance layer — the SP never gets a token, so it can't call any Fabric API.
  • This same protection extends to Azure Resource Manager, Key Vault, SQL, Storage, and any OAuth-protected resource.

💥 Test D — Multi-resource burst sign-in (lateral movement pattern)

What it proves: a service principal authenticating across many different Azure resources in a short burst mirrors lateral movement — an attacker enumerating what resources the SP can reach.

Service principal: POC-Test-D-BurstSignIn

🎬 Why this SP is confirmed compromised The SOC's SIEM correlation rule detects that POC-Test-D-BurstSignIn authenticated to 7 different Azure resources within 10 seconds — Graph API, ARM, Key Vault, Storage, SQL, Power BI, and Fabric. This SP normally only accesses Azure SQL. The burst pattern is consistent with an attacker enumerating what the compromised credential can reach (MITRE T1078 — Valid Accounts + T1087 — Account Discovery). The SOC confirms the SP as compromised.

Steps

PowerShell 
$tenantId     = "<Your Tenant ID>"
$clientId     = "<POC-Test-D Application (client) ID>"
$clientSecret = "<POC-Test-D Secret Value>"

$resources = @(
    "https://graph.microsoft.com/.default",
    "https://management.azure.com/.default",
    "https://vault.azure.net/.default",
    "https://storage.azure.com/.default",
    "https://database.windows.net/.default",
    "https://analysis.windows.net/powerbi/api/.default",
    "https://api.fabric.microsoft.com/.default"
)

foreach ($scope in $resources) {
    $body = @{
        grant_type    = "client_credentials"
        client_id     = $clientId
        client_secret = $clientSecret
        scope         = $scope
    }
    try {
        $r = Invoke-RestMethod -Uri "https://login.microsoftonline.com/$tenantId/oauth2/v2.0/token" `
            -Method POST -Body $body -ContentType "application/x-www-form-urlencoded"
        Write-Host "OK: $scope"
    } catch {
        Write-Host "FAIL: $scope (expected if no API permission)"
    }
    Start-Sleep -Seconds 1
}

This generates sign-in events across 7 different Azure resources in rapid succession.

SOC responds — confirm the SP as compromised

Graph 
POST https://graph.microsoft.com/v1.0/identityProtection/riskyServicePrincipals/confirmCompromised

{
  "servicePrincipalIds": ["<POC-Test-D Service Principal Object ID>"]
}

Verify

  1. Wait 15–30 minutes for sign-in logs to populate
  2. Go to Entra admin center → Identity → Monitoring → Sign-in logs → Service principal sign-ins
  3. Filter by POC-Test-D-BurstSignIn — you should see sign-in entries for each resource
  4. In production, this burst pattern would trigger Entra's ML-based detection of anomalousServicePrincipalActivity
  5. Verify the SP appears in Protection → Identity Protection → Risky workload identities

What to show the customer

  • A legitimate SP typically accesses 1–2 resources — a burst across 7 resources is a red flag for lateral movement.
  • Entra's ML engine uses this pattern data to build behavioral baselines for each SP.
  • In production, if the SP shifts to accessing new resources it never used before, Entra flags it as Medium risk automatically.
  • In the POC, the SOC manually confirms compromised to simulate the end-state of that automated detection.
  • This is invisible to the attacker — no agent or sensor required, just token issuance telemetry.

🛑 Test E — CA enforcement: full block demonstration

What it proves: switching the CA policy from report-only to enforce mode immediately blocks a risky SP from obtaining tokens for any resource.

Steps

  1. Ensure the SP is marked as compromised — POST to confirmCompromised with body {"servicePrincipalIds": ["<Service Principal Object ID>"]}, then wait 1–2 minutes for risk to propagate.
  2. Verify the SP is risky — Protection → Identity Protection → Risky workload identities → confirm POC-RiskyWorkloadIdentity shows High risk.
  3. Switch the CA policy to enforce mode — Protection → Conditional Access → Policies → open POC - Block Risky Workload Identities → change Enable policy from Report-only to On → Save.
  4. Wait 1–2 minutes for policy propagation.
  5. Test the block — run this in PowerShell:
PowerShell 
$body = @{
    grant_type    = "client_credentials"
    client_id     = "<Application (client) ID>"
    client_secret = "<Secret Value>"
    scope         = "https://graph.microsoft.com/.default"
}
try {
    Invoke-RestMethod -Uri "https://login.microsoftonline.com/<Your Tenant ID>/oauth2/v2.0/token" `
        -Method POST -Body $body -ContentType "application/x-www-form-urlencoded"
    Write-Host "NOT BLOCKED (unexpected)"
} catch {
    Write-Host "BLOCKED!" -ForegroundColor Red
    $_.ErrorDetails.Message | ConvertFrom-Json | Select-Object error, error_description | Format-List
}
  1. You should see:
Error
AADSTS53003
Message
Access has been blocked by Conditional Access policies. The access policy does not allow token issuance.
  1. Try multiple resources — Graph, Fabric, ARM, Key Vault — they should ALL be blocked.
  2. Revert the CA policy to report-only after the demo: change Enable policy back to Report-only → Save.
⚠️ Don't leave the demo in enforce mode Step 8 is not optional housekeeping — reverting to report-only is what keeps this POC "no production impact" if the SPs are ever reused or the policy scope is later widened.

What to show the customer

  • The block happens at the token issuance layer — the SP can't get a token for any resource.
  • The error code AADSTS53003 clearly identifies Conditional Access as the reason.
  • Switching between report-only and enforce is instant — no downtime, no app changes.
  • In production, SOC teams can enforce the policy to immediately contain a compromised SP.
  • After investigation, dismiss the risk to restore access — no secret rotation needed if the SP wasn't actually compromised.

🧹 Cleanup

When the POC is complete, clean up all test resources. Do this in order — reverting the policy first avoids blocking yourself out of the deletion steps.

  1. Revert the CA policy — if in enforce mode, switch back to report-only or delete the policy.
    • Protection → Conditional Access → Policies → POC - Block Risky Workload Identities
  2. Dismiss all risks — Protection → Identity Protection → Risky workload identities → select all POC SPs → click Dismiss risk.
  3. Delete the app registrations (this also removes the associated service principals):
    • POC-RiskyWorkloadIdentity (Core POC)
    • POC-Test-A-AdminConfirm
    • POC-Test-B-BackdoorCred
    • POC-Test-C-FabricAccess
    • POC-Test-D-BurstSignIn
    • POC-LeakedCredentialTest (if created)
  4. Remove Fabric API permissions — if any test SPs were granted Tenant.Read.All on Power BI Service, the deletion above handles it.
  5. Delete the CA policy if no longer needed.
